# 活人感风格契约（去 AI 味）

> S3 写作前必读；R5 人味审读按本文件审计。目标：读者觉得"是真人在讲他做过的事"，不是"模型在整理信息"。
> 优先级：用户 voice profile（见 §5）> 本契约。审计是 detect-only：只出"问题→修复表"，修复由写作流程做，禁止审计时发明事实。

## 1. 词汇层

**硬黑名单（全文命中数必须为 0，逐词搜索）**
- 结构套话：综上所述 / 总而言之 / 总的来说 / 值得注意的是 / 需要指出的是 / 不难发现 / 由此可见 / 让我们来看看 / 接下来我们 / 众所周知 / 显而易见 → 删掉，直接说那件事
- 论述枚举：首先…其次…最后（全文 ≤1 组，且必须跨小节；段落内禁止）
- 学术腔翻译腔：本质上 / 换句话说 / 换言之 / 不可否认 / 旨在 / 鉴于 / 一定程度上 / 某种意义上 / 深入探讨 / 深入剖析 → 换短词或直接删
- 互联网黑话：赋能 / 抓手 / 发力点 / 闭环 / 颗粒度 / 底层逻辑 / 沉淀 / 打法 / 组合拳 / 护城河 → 说清楚到底帮谁做了什么
- 模糊归因：业界普遍认为 / 专家指出 / 有研究表明 / 不少开发者反馈（命中数=0）→ 给可查来源，或改成"我自己在两个项目里碰到的是…"

**空洞评价词**：出现"大幅/显著/极大 + 提升/优化"时，句内必须有数字（版本号/百分比/耗时/内存），否则改写成具体事实（"效率提高了约 50%，从 40 分钟降到 22 分钟"）。

**词汇简单化**：用而不用"利用"、改而不用"进行修改"、开始而不用"着手开始"；"进行/完成 + 名词化动词"每千字 ≤1 处。

**中英混排**：专有名词首次给英文原名（Kubernetes（下文简称 k8s））；报错/命令/API/日志保留英文原文用等宽；缩写首次给全称；禁炫技式夹杂（"这个 case 很 interesting"命中即改）。

## 2. 句式层

1. **句长节奏**（burstiness）：连续 3 句同长度区间（15–30 字）→ 必拆或必并；每段最长句 ≥ 2×最短句；短句（<10 字）占比 ≥10%；单句成段全文 ≥3 处。
2. **三连禁令**：同构三项排比 → 保留两项或拆两句；"不是 A，而是 B"每千字 ≤1、全文 ≤3；句尾拔高（"，体现了/彰显了/凸显了/从而保证了"）出现即删。
3. **小标题**：禁止相邻标题字数相等结构相同（"为什么快/为什么稳/为什么省"= 公式化）。
4. **标点纪律**：破折号全文 ≤3 且同段不叠；正文冒号每千字 ≤2；感叹号 ≤2；省略号 ≤3；零 emoji；加粗每小节 ≤1 且禁止"**标签：** 内容"式列表。
5. **句构**：无主语被动每千字 ≤2；同一主语连续开头 3 句即改；同一事物全文固定一个叫法（禁"该框架/此工具/这一系统"轮换）。

## 3. 内容层（人味锚点，7 类）

1. **第一手踩坑**：时间+环境+版本+现象（"在 Ubuntu 22.04 + CUDA 12.1 上跑通的，换 11.8 直接段错误"）
2. **具体数字**：版本号、耗时、QPS、内存峰值、issue 编号、对比基准
3. **现场原文**：真实报错栈、日志行、可吐槽的官方文档原话
4. **观点-让步-反驳**：先承认对立面合理再给判断（每篇 ≥1 处）
5. **诚实的不知道**："这里我没搞明白""这块有争议，两种都有人在用"（每篇 ≥1 处，宁缺毋滥地编出确定性是 AI 最大破绽）
6. **弃案记录**："试过 A，放弃了，因为…"（写出放弃的具体代价）
7. **口语插入**：括号题外话、承认跑题拉回（"扯远了，回到部署"）（全文 2–4 处）

**密度底线**：人味锚点合计 ≥3 处/千字，其中第 1–3 类 ≥1 处/千字；体感型情绪表达全文 2–3 处；比喻全文 ≤3 处且不拆子比喻；每个核心观点必须落到具体支撑，纯论断段=违规。

**反面禁令**：禁编造案例（"比如有一次，一个用户…"没有素材就写"我自己没试过，按文档推测…"）；禁空泛指代（"某些框架"→写具体名字或删句）；禁伪深度句式（"真正的问题在于/归根结底是"）；禁"挑战与展望"模板结尾——收尾落在最后一个具体事实或明确判断上；小标题下首句禁止复述标题。

## 4. 允许保留的套路（技术文结构感豁免，审计不得标记）

小标题本身；真正的并列项编号列表（≤3 连条，每条完整句）；开头 TL;DR；跨小节的"首先/其次"（全文 ≤1 组）；让步-反驳结构本身；真正要读者停下的"注意"（安全警示/版本不兼容——判据：删掉会不会踩坑）；代码块、表格、图示引用。

## 5. Voice Profile（`references/voice-profile.md`）

- **建立**：G2 归档终稿时，从 writing-samples/ 最近 3–10 篇提炼增量：平均句长与短句占比、高频转场词/口头禅前 10、每千字"我"密度、比喻频率与取材领域、小标题风格、数字密度、收尾方式、括号插入语频率、中英混排习惯、情绪强度。首次运行时创建该文件，之后增量 diff。
- **使用**：G0 简报时加载；S3 写作与 R5 审计时作为比对基准。**样本频率 > 契约上限**：若用户历史文章破折号很多，按样本保留，不执行本契约上限。

## 6. AI 味审计的流水线位置

```
S3 初稿（带 voice-profile + 本契约）
  → R5 人味审读（独立子 Agent，detect-only，只读成稿不读需求背景——防作者盲区）
      输出《问题→位置→模式→修复建议》表 + AI味快检清单逐条勾选
  → 写作流程按表修复（整段重写，不做词级替换；禁止新增版本号/数字/日期/引用）
  → 复审只回答两问：① 哪段还像 AI？② 修复有没有增删事实？
```

**AI 味快检清单（R5 逐条打勾，任一不过即出修复项）**：①黑名单零命中 ②无模糊归因 ③评价词带数字 ④句长有起伏 ⑤排比克制 ⑥标点合规 ⑦锚点达标 ⑧有真实的不确定 ⑨有让步 ⑩比喻克制 ⑪指代固定 ⑫收尾落地 ⑬事实守恒 ⑭抽 3 段通读盲测——是"人在讲做过的事"不是"模型在整理信息"。

> 经验：黑名单会催生替身词（"不是A而是B"实测最难禁），第 ⑭ 条通读盲测是最终兜底；标点禁令（破折号 ≤3）性价比最高。审计两次不过 → 交人工终审，不无限迭代。
