# R3 深度批评（Devil's Advocate）

- 审稿对象：`draft-v1.md`（pi 解剖）
- 审稿口径：**只判深度**——懂行读者会在哪里追问"然后呢？"。不判文风、不判事实准确性；文中已标注"单源/转引/推断"的地方（星数、Reddit 转引、oh-my-pi、TS 门槛推断）一律不再罚。
- 素材基准：`research/findings-a/b/c/d.md`。

理由一句话：批判章和立场自省是超 README 的真深度，但所有机制段（ARCH/PHILOSOPHY/HANDS-ON/EXTENSIONS）停留在"能力清单复述"，没有一个机制被走到"读者能想象它怎么运转"的那一步；且 EXTENSIONS 章开出的期票（"这笔账，下一章算"）在账单章没有兑现。对目标读者（会去读 internals 的工程师）而言，这篇文章在最需要深的地方最浅。

## 一、浅处清单（位置 → 缺什么 → 素材在哪 → 建议补法）

### S1. Agent loop 只有一句能力罗列，没有一轮对话的消息流走查
- **位置**：L33（"流式输出、工具参数聚合、执行工具、把结果回填进上下文，全在这一层，一直循环到模型不再发起工具调用为止"）。
- **缺什么**：这是 findings-a §1.1 原话的直译压缩，四个动词排成一行，读者仍然画不出一轮对话的消息序列：user 消息 → assistant 返回带 tool_use 块 → 工具执行 → 结果作为 tool message 追加进 context → 再次请求 → 直到无 tool_use。"工具参数聚合"是四个词里最专业的一个，恰恰零解释（流式返回的 tool 参数是分片 delta，需要拼装校验后才可执行）——这正是"参数聚合"存在的理由，一句就能讲明白。TypeBox 同病（L33"带 TypeBox schema 校验"：为什么选 TypeBox 而不是 zod/json-schema，一亿次没提）。
- **素材**：findings-a §1.1、§1.2、§1.3。
- **建议补法**：在 ARCH 章插入一个 5 行的"一轮消息流"示意（纯文字即可），并把"工具参数聚合"展开成一句机制解释。这是全文最该有一张图而只有一句话的地方（fig-2 现在画的是包分层，不是消息流）。

### S2. "跨 provider 的上下文接力"列名未释——它才是 /model 热切换的机制底座
- **位置**：L33（脏活清单末项）、L35（模型接入面"宽"）、L83（`/model` 换模型）。
- **缺什么**：文章把多 provider 当成一张清单报菜名，但 pi 的 provider 支持比别家深的点在于：中途换模型（`/model`、Ctrl+P 轮换）依赖 pi-ai 把上下文在不同 provider 的消息格式间做规范化接力。读者问"然后呢"：换模型那一刻，上一家的 thinking 块、工具调用记录怎么办？这层机制一个字没有，导致 L35 和 L83 两处成了不相连的孤岛。
- **素材**：findings-a §1.3、§4.2；findings-b 二（`pi --model sonnet:high` 语法、`/scoped-models`）。
- **建议补法**：在 L35 或 L83 处用两三句把"宽"落到机制上：宽不是"能调很多 API"，是"会话可以在任意时刻跨家换乘，上下文不落地"。

### S3. "<1000 tokens" 只给数字不给内容——系统提示词里写了什么才是论点的下半句
- **位置**：L41（"系统提示词加全部工具定义，加起来不到 1000 tokens"）。
- **缺什么**：压轴数字孤零零挂着。短不是目的，"短了还能干活"才是论点，而证据就在 findings 里：提示词里有两条精心设计——autonomy 指令（"You don't need to ask for permission. The user expects you to work autonomously..."）和未知符号 grounding 指令（"If you identify an unknown symbol, function, or API: list all relevant candidate sources..."）。这两句恰恰回答了懂行读者最自然的质疑："这么短的提示词，hallucination 和瞎猜怎么办？"——答案就在提示词自己身上。
- **素材**：findings-a §2.3（含逐字引文）。
- **建议补法**：摘录系统提示词开头一两句 + grounding 指令，两行引文换一个论点的下半句，性价比极高。

### S4. 四工具"对模型友好"只有结论没有机理：read 分页与 edit 模糊匹配各欠一句
- **位置**：L47（"read 带分页和行号，能读图片；write 整文件覆盖；edit 用简单的 diff 格式加模糊匹配"）。
- **缺什么**：L47 末尾说"模型都被训练过处理这种最小 schema"，但这个论点没有被落到具体工具上：①read 的分页 + 行号之所以好用，是因为各家模型都被训练过处理这种分页式 read 输出（findings-a §2.4 明说）；②edit 的模糊匹配之所以存在，是**为了容忍模型输出里的细微空白差异**——模型复述 old_string 时缩进/空白经常漂移，精确匹配会大面积失败，fuzzy matching 是给模型的容错垫（findings-a §2.5）。现在文章里"模糊匹配"读起来像一个随意的技术选型，实际上它是四工具哲学能成立的承重墙之一。
- **素材**：findings-a §2.4、§2.5、§2.1。
- **建议补法**：PHILOSOPHY 章给 read 和 edit 各补一句"为什么这个形状对模型友好"。这是任务书里点名要查的两处之一。

### S5. 会话树 entry(id/parentId) 有名词无机制——读者无法"想象"
- **位置**：L83（"每个会话是个 JSONL 树……连按两次 Escape 直接进树视图，跳回任意节点接着聊"）。
- **缺什么**：这是任务书点名的第二处。现在的写法是 UI 功能清单（Escape 两下、/fork、/clone、/compact），底下的数据结构只有"JSONL 树"四个字。entry 长什么样？`id`/`parentId` 怎么把消息串成树？active leaf 是什么？跳回旧节点后新消息挂在哪（必然是 parent 指向该节点、旧分支保留）？切换分支时被放弃分支还可以摘要后挂到新位置（branch summaries）——这个细节既机制又有画面感，完全没进文。缺了这些，"会话树"和任何产品的 history 列表在读者眼里没有区别，而这本是 pi 最有辨识度的机制。
- **素材**：findings-a §3.2（id/parentId/active leaf 逐字引文）、§3.6（branch summaries）；findings-b 三（/fork 与 /clone 的语义差异：fork 从旧 user message 开新文件并把 prompt 放回编辑器，clone 复制整条 active branch 且编辑器为空——文章并提两命令却未区分）。
- **建议补法**：给一行真实（或示意）的 JSONL entry + 三句话讲 active leaf 与跳转语义；branch summaries 与 fork/clone 之别各一句。

### S6. headless JSON/RPC 一句话带过——"焊进自己的程序"的接口形状与用途全空
- **位置**：L37（"headless 模式走 JSON 流或 RPC，意味着你可以把 pi 当零件焊进自己的程序里"）。
- **缺什么**：这是全文对"底盘论"最硬的支撑，却只有一个比喻。然后呢：JSON 流长什么样（事件序列）？RPC 走 stdin/stdout 还是 HTTP/WebSocket？谁在这么用（OpenClaw 正是"把 pi 当 SDK 焊进程序"的最大实例，文章 L23 提了 OpenClaw 却没和这里接上）？pi-agent-core 的 HTTP/WebSocket/内存三种 transport 抽象（findings-a §1.4）正好是这段的下文，也没接。
- **素材**：findings-a §1.4、§1.5；findings-c 三（运行形态行明确列了 TUI/print/JSON 脚本/stdin-stdout RPC/SDK 多形态）。
- **建议补法**：EXTENSIONS 或 COMPARE 章补一小段：headless 的两种形态 + OpenClaw 即活例。把 L23 的伏笔在这里收掉。

### S7. `--ignore-scripts` 印在代码块里却从未解释；供应链硬化零字
- **位置**：L70（安装命令本身含 `--ignore-scripts`）、L62（安全段只有"放容器里"）。
- **缺什么**：这是最扎眼的一处"机制躺在自己代码块里没被解释"。findings-b 一有现成解释：该 flag 禁用依赖安装期的生命周期脚本，pi 正常安装不需要 install scripts——这既是给用户的提醒也是项目自身供应链姿态的自白。而 findings-c 二的对比表里还躺着更硬的一排货：**依赖精确锁版、min-release-age=2、shrinkwrap、生命周期脚本白名单**。一个"无权限系统、裸跑用户权限"的项目，恰恰因为要裸跑才把供应链硬化做到这个程度——这层"极简与安全的关系"文章完全没讲，安全段（L62）只讲了环境侧一半。
- **素材**：findings-b 一（`--ignore-scripts` 逐字说明）；findings-c 二（安全姿态行：供应链硬化四件套）。
- **建议补法**：HANDS-ON 安装处一句解释 flag；安全段补三句供应链硬化。注意这同时是给 CRITIQUE 章的反方补强——不写它，"无权限系统"一段是单边叙事。

### S8. pi package 是什么没讲：manifest 结构与安装警告缺失
- **位置**：L120（"第三方分发走 `pi install npm:@foo/pi-tools` 或 `pi install git:...`"）。
- **缺什么**：读者读完只知道"能装"，不知道"装的是什么"：一个 pi package 是在 package.json 里挂 `"pi": {"extensions": [...], "skills": [...], "prompts": [...], "themes": [...]}` 清单的包，npm 上以 `keywords: ["pi-package"]` 聚合检索。更关键的是 README 那句安全警告："Pi packages run with full system access. … Review source code before installing third-party packages."——这句话和 L62 的安全叙事、L122 的"装别人做好的包"是同一条线，缺席后"装包"读起来毫无风险感，与全文的审慎人设不符。
- **素材**：findings-b 五。
- **建议补法**：EXTENSIONS 章补 manifest 四键一句话 + "包以完整系统权限运行"的警告一句。

### S9. /login 双轨只讲了操作没讲含义：订阅额度 vs API 计费是真实成本的分水岭
- **位置**：L81（"登录两条路：环境变量喂 API key……或者 `/login` 走订阅，认 Claude Pro/Max、ChatGPT Codex、GitHub Copilot 三家"）。
- **缺什么**：双轨的经济含义没展开：订阅登录 = 用已有的包月额度跑 agent（边际成本近零），API key = 按 token 计费。对一个"算账"的文章（CRITIQUE 章标题就叫算账），这是最具体的一笔账，反而没算。另外 findings-b 二里的 provider 列表比正文"约 30 家"更有信息量的部分被抹平了：Xiaomi MiMo、ZAI Coding Plan (Global/China)、OpenCode Zen、Cloudflare AI Gateway 这类区域/网关型条目，恰好说明它的接入面是按"真实世界的付费路径"长的，不是凑数。
- **素材**：findings-b 二。
- **建议补法**：一句话点破双轨含义即可，不必展开成经济学论文。

### S10. Windows 段只给存在性证据，漏了实操坑
- **位置**：L79（"Windows 用户不用绕路，官方有 install.ps1……"）。
- **缺什么**：findings-b 三里有一个现成的、有画面感的坑没进文："On Windows Terminal, `Alt+Enter` is fullscreen by default. Remap it in docs/terminal-setup.md"——而 Alt+Enter 恰是 L85 刚讲完的 follow-up 排队键。安装能跑和键位顺手是两回事，HANDS-ON 章漏掉这个坑等于在自家重点章节留了个反例缺口。（不罚"未验证 Windows 支持好坏"——findings-d 明确无证据不写，文章也没写过头。）
- **素材**：findings-b 三（消息排队节末尾）。
- **建议补法**：L85 讲完 Alt+Enter 后补半句 Windows Terminal 需重映射。

## 二、边界与反例：任务规模维度整体缺席

### B1. "五种情况别用 pi"全是用户类型边界，没有一条任务规模边界
- **位置**：L162。
- **缺什么**：清单答的都是"你是什么人"，没答"你干什么活"。反例现成：几万文件的单体仓库——默认没有 grep/find/ls（findings-d 二："长任务并行、大型仓库检索都要用户自己搭"），检索全靠模型现写 bash 命令；需要并行的长任务——无 sub-agent、无后台 bash，测试矩阵只能串行 + 手工 tmux。这些不是"没造好"，是设计使然，但"设计使然"恰恰需要文章替读者把场景代价显式算出来，而不是停在工具清单层面（Reddit 帖列的是清单，文章的职责是越过清单）。
- **素材**：findings-d 二、三焦点 1；findings-a §2.7（可选只读工具默认关闭）。
- **建议补法**：CRITIQUE 章在"无现成生态"之后加一小节"规模边界"：仓库规模、任务并行度、长任务三问。

### B2. 长任务的上下文管理只讲了"有 /compact"，没讲"满了会怎样"
- **位置**：L83（"/compact 手工压缩上下文"）、L85（steering/follow-up 被推荐为"最值得练熟的操作"）。
- **缺什么**：文章把会话树和消息排队包装成"长任务利器"，却没走查长任务真正的瓶颈：上下文满了之后发生什么？pi 的答案是手工 `/compact`（可带自定义指令，findings-a §3.4）或自装 custom-compaction 扩展（L122 提到过这个示例名，但没和上下文管理接上）。"极简在长任务里的表现"这个问题，文中只答了交互半边，没答资源半边。
- **素材**：findings-a §3.4；findings-b 五（custom-compaction 在示例名单里）。
- **建议补法**：L83 处两句话把 /compact 的语义（可带 prompt 的手工压缩）与其在长任务中的位置讲清，并回接 L122 的 custom-compaction 示例。

### C2. 容器化的运维成本只字未算

- **素材**：findings-a §2.8（containerization.md 存在）；findings-d 二（无内置护栏，风险依赖用户配置）。
- **建议补法**：L62 补两三句运维账，或明确承认"这笔运维账本文没算"，都比现在的干净利落诚实。

### C3. 金钱账缺席：订阅 vs 按量的真实成本变量没进账单
- **位置**：CRITIQUE 章整体。
- **缺什么**：见 S9。四笔账全是抽象成本（生态、门槛、风险），没有一笔是一美元级的。用 pi 每月花多少钱（订阅额度内 vs API 账单）是用户决策的第一变量，素材现成。
- **素材**：findings-b 二。
- **建议补法**：并入第五笔账或单独一行。
